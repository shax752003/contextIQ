PROJECT DOCUMENTATION: Industrial Document Multimodal-RAG System
================================================================

0. SIMPLIFIED EXECUTIVE SUMMARY (For Non-Technical Readers)
-----------------------------------------------------------
Imagine you have thousands of technical manuals, diagrams, and specification sheets for industrial machinery. If you upload these to a standard AI chatbot (like ChatGPT), it often fails because it cannot "read" the complex tables or understand the engineering diagrams properly. It might give you a wrong answer because it missed a critical number hidden in a spreadsheet row.

This project creates a "Smart Assistant" that solves this by treating every part of the document differently:
1. It reads text like a human.
2. It processes tables like a spreadsheet analyst, preserving the rows and columns.
3. It looks at images and scans (OCR) like a vision system.

When you ask a question like "What is the max pressure for Valve X?", it doesn't just guess. It looks up the exact table row in the correct manual, verifies the information, and gives you an answer backed by a citation (e.g., "Source: Specification Manual, Page 42"). It is designed to be "idempotent" (can resume if crashed) and "read-only" (cannot accidentally delete data), making it safe for business use.

3. ARCHITECTURE FLOW
--------------------
The system follows a strict linear pipeline architecture for data processing, separating the "WRITE" path (Data Engineering) from the "READ" path (Application Serving).

A. The Offline Pipeline (Data Engineering Channel)
   This runs as a batch process, ensuring data quality and consistency.

   Step 1: Ingestion
   - Scans the `data/raw` directory for new PDF files.
   - Validates file types and integrity.
   - Extracts metadata (file size, page count, creation date) for traceability.
   - Output: A metadata registry (CSV).

   Step 2: Multimodal Extraction
   - This is the heavy lifting layer. It routes different parts of the PDF to specialized extractors:
     * Text: Extracted via Docling/PyMuPDF to preserve reading order.
     * Tables: Extracted via Camelot to CSV format (preserving row/column structure).
     * Images: Extracted via PDF2Image/PyMuPDF.
     * OCR: Applied to extracted images using Tesseract to capture embedded text.
   - Key Feature: Idempotency. It checks if extraction artifacts already exist to avoid re-running expensive OCR.

   Step 3: Modality-Aware Chunking
   - Instead of blindly cutting text every 500 characters, it chunks based on type:
     * Text: Recursive Character Splitting (respects paragraphs).
     * Tables: Row-based chunking (keeps table headers with rows).
     * Images: Treated as discrete units.
   - Key Feature: Deterministic Hashing. Every chunk gets a unique SHA-256 hash based on its content + source + page. This allows us to detect duplicates instantly.

   Step 4: Embedding & Indexing
   - Converts chunks into 384-dimensional vectors using the Sentence-Transformers model (all-MiniLM-L6-v2).
   - "Deduplication Strategy": Before inserting into the Vector Database (ChromaDB), it checks the existing IDs. If a chunk hasn't changed, it isn't re-embedded. This saves massive compute costs and prevents duplicate search results.
   - Metadata Injection: Every vector is tagged with {source_file, page_number, modality_type, chunk_id}.

B. The Application Layer (Serving Channel)
   This is the user-facing part, running purely in "Read-Only" mode to prevent data corruption.

   1. User Query: User asks a technical question.
   2. Retrieval:
      - The query is embedded using the same model.
      - ChromaDB performs a similarity search (cosine similarity).
      - Top-K results (e.g., top 6) are retrieved.
   3. RAG Generation:
      - The retrieved text/tables are injected into a strict prompt template.
      - The LLM (Google Gemma via OpenRouter) generates an answer.
      - The prompt forces the LLM to cite its sources and say "I don't know" if the context is missing.

4. CODEBASE STRUCTURE & FILE BREAKDOWN
--------------------------------------

ROOT DIRECTORY
- main.py: The single entry point for the application. It handles environment setup (API keys) and runs the query loop. It deliberately does NOT import the heavy pipeline logic to keep startup fast.
- requirements.txt: pinned dependencies.
- .env: Stores secrets (OPENROUTER_API_KEY) and config (DATASET_VERSION).
- Dockerfile: Containerization config for deployment.

DIRECTORY: app/ (The Application Core)
- config.py: The Central Nervous System.
  * Defines all paths (`data/v1/raw`, `data/v1/chroma_db`).
  * Manages versioning (DATASET_VERSION).
  * Stores constants (CHUNK_SIZE=700, RETRIEVER_K=6).
  * Loads environment variables.
- rag.py: The Orchestrator.
  * `rag_answer(query)`: The main function called by main.py.
  * Connects Retrieval -> Prompting -> LLM.
- retrieval.py: Vector Logic.
  * `get_vectorstore()`: Initializes ChromaDB. Crucially, it throws an error if the DB doesn't exist, enforcing the "Read-Only" rule.
  * `deduplicate_chunks()`: Logic to remove redundant context before sending to LLM.
- embeddings.py: Model Wrapper.
  * Initializes the HuggingFaceEmbeddings model consistently across the app.
- utils.py: Helpers.
  * `load_chunks()`, `save_json()`, `is_pdf()`.
- manifest.py: Pipeline Tracking.
  * Manages `pipeline_metadata.json`. Records every run's success/failure status, timestamp, and configuration. This is vital for auditing.
- hashing.py: Data Integrity.
  * `get_chunk_id()`: Generates the SHA-256 hash for deduplication.

DIRECTORY: pipelines/ (The Data Factory)
- run_all.py: The Master Switch.
  * Runs Ingest -> Extract -> Chunk -> Embed in order.
  * Logs progress to the Manifest.
  * Handles error reporting for each stage.
- ingest.py: Step 1 logic.
- extract.py: Step 2 logic. Handles the complex multi-library extraction (Docling, Camelot, Tesseract).
- chunk.py: Step 3 logic. Applies specific splitting strategies per modality.
- embed.py: Step 4 logic. Handles the loading of chunks and the intelligent deduplicated insertion into ChromaDB.

DIRECTORY: data/ (The Storage Layer)
- Structured by version: `data/v1/`, `data/v2/`.
- raw/: Original PDFs.
- extracted/: Intermediate JSONs, CSVs, and PNGs.
- chunks/: Cleaned, chunked JSONs ready for embedding.
- chroma_db/: The persistent Vector Database on disk.

5. KEY DESIGN DECISIONS (FOR INTERVIEWS)
----------------------------------------

1. Why "idempotency"?
   In production, pipelines fail. If the pipeline crashes at 99%, we shouldn't re-process the first 99% on retry. By using deterministic hashing and checking for existing artifacts, our pipeline can resume or skip work automatically.

2. Why separate "app" and "pipelines"?
   Security and Stability. The web server (App) should never have permission/ability to write to the core database. It only reads. The Pipeline (Admin) writes. This separation prevents race conditions and accidental data corruption.

3. Why Dataset Versioning?
   If we change the chunking strategy (e.g., chunk size 500 -> 1000), we destroy the consistency of the current vector index. Versioning (`data/v2`) allows us to A/B test new strategies without breaking the live application (`data/v1`).

4. Why Multimodal?
   Technical docs depend heavily on tables and diagrams. Ignoring them (standard RAG) leads to wrong answers. By explicitly extracting tables as CSVs and embedding them, we allow the LLM to "read" the data rows accurately.

6. FUTURE IMPROVEMENTS
----------------------
- Hybrid Search: Combining Vector search (Semantic) with BM25 (Keyword) for better exact matches (part numbers).
- Multi-Vector Retriever: Storing a summary of a chunk for searching, but passing the full chunk to the LLM.
- Visual RAG: Using a VLM (Vision-Language Model) to answer questions directly from the diagram images.
